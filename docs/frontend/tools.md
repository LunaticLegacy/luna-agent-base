# 前端工具板实现说明

本文只梳理当前前端 `tools` 页面在代码里的真实实现，不描述尚未接通的想法或设计稿。

## 页面位置

- 页面组件：`frontend/angelus/src/app/pages/tools.page.ts`
- 状态来源：`frontend/angelus/src/app/services/state.service.ts`
- 数据接口：`frontend/angelus/src/app/api.service.ts`

## 当前展示的工具信息

工具板以“工具管理”为标题，顶部提供一组统计卡片，下面是工具列表表格，底部在选中某个工具后展示详情面板。

### 统计卡片

页面顶部展示 5 个统计项：

- 总工具数
- 可用工具
- API 工具
- 本地技能
- 今日调用

这些统计值来自 `StateService.toolStats()`。当前实现里：

- `total` 取工具列表长度，若没有加载到工具列表，则回退到当前 Swarm 的 `tool_count`
- `available` 直接等于当前可用工具数量
- `api` 固定为 `0`
- `local` 直接等于当前可用工具数量
- `calls` 为当前工具调用次数之和

这说明前端已经预留了 API 工具 / 本地技能的统计展示，但实际统计口径还没有细分到 API 工具。

### 工具表格

表格当前展示以下字段：

- 工具名称
- 类型
- 状态
- 描述
- 调用次数
- 平均耗时
- 最后调用
- 操作

每行工具来自 `StateService.derivedTools()`，页面点击行后会将该工具设为当前选中项。

当前列表项在代码中包含这些展示字段：

- `id`
- `name`
- `icon`
- `type`
- `status`
- `desc`
- `calls`
- `avgMs`
- `lastCall`
- `successRate`
- `errorRate`
- `created`
- `schema`

## 数据来源与加载逻辑

### 优先级

工具数据有两层来源：

1. 如果 `toolsLoaded` 为 `true`，直接使用 `state.tools()`
2. 如果还没加载到工具列表，则从当前 Swarm 的 graph 里提取 `ToolNode`

### 接口加载

`StateService.loadTools()` 会调用 `ApiService.listTools(baseUrl, {})`，也就是：

- `GET /api/tools`

返回后会把 `response.tools` 映射成页面所需的 `ToolItem`。

### graph 回退数据

如果工具列表没有拉到，前端会从 graph 中筛选 `node_type === 'ToolNode'` 的节点，构造一个临时的工具视图。

这套回退逻辑目前带有明显的占位性质：

- `icon` 固定为 `🔧`
- `type` 固定为 `本地`
- `status` 固定为 `online`
- `calls`、`avgMs`、`successRate`、`errorRate` 都是前端推算的默认值
- `created` 和 `lastCall` 也不是后端真实返回值
- `schema` 只尝试读取节点里的 `input_mapping`

也就是说，当前工具页能展示“工具节点”的结构，但在 graph 回退模式下并不是真实的工具运维数据。

## 查询和筛选控件

工具页顶部有一组看起来像筛选区的控件：

- “全部工具 / API 工具 / 本地技能 / 已禁用” 标签页
- 工具名称搜索框
- 类型下拉框
- 状态下拉框

但从当前代码看，这些控件都只是静态渲染，尚未绑定实际过滤逻辑：

- 标签页没有点击处理
- 搜索框没有输入事件
- 下拉框没有绑定筛选状态
- 表格数据仍然直接渲染 `state.derivedTools()`

所以目前它们更像是 UI 占位，而不是可工作的查询系统。

## 详情面板

点击某一行后，会把工具设为 `selectedTool`，页面下方展开详情面板。

详情面板包含三块：

### 基本信息

- ID
- 类型
- 状态
- 创建时间

### 调用统计

- 总调用
- 成功率
- 平均耗时
- 错误率

### 参数定义

- 直接把 `schema` 以 JSON 形式渲染到代码块里

这个面板的数据全部来自当前选中的 `ToolItem`，属于纯展示型详情。

## 已有操作入口

界面上已经摆出了几个操作按钮：

- `注册新工具`
- 行内 `详情`
- 详情面板里的 `测试调用`
- 详情面板里的 `编辑`
- 详情面板里的 `禁用`

不过这些按钮当前都没有绑定实际处理函数，点击后不会触发真正的创建、测试、编辑或状态变更流程。

## 目前缺失的 CRUD / 动作支持

当前前端对工具板的能力，基本停留在“查看”层级，缺少这些完整动作：

- 新增工具
- 编辑工具
- 删除工具
- 启用 / 禁用工具
- 真实的测试调用
- 工具详情跳转或独立详情页
- 搜索、筛选、分页联动
- 工具统计的后端实时汇总

另外，`ApiService` 里虽然已经有知识库、记忆库等资源的增删改接口，但工具资源只看到 `listTools()`，没有对应的工具 CRUD 接口包装。

## 结论

当前工具板已经具备一个比较完整的“目录页 + 详情页”外观，也能从 `/api/tools` 拉取真实工具列表；如果接口不可用，还能从当前 Swarm graph 中回退出一个工具视图。

但从交互能力上看，它还是一个偏展示型的页面：

- 数据加载有了
- 展示结构有了
- 筛选和动作入口有了
- 真正可用的过滤、CRUD、测试和状态变更还没有接通
